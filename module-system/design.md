### 讨论确认记录

| # | 议题 | 结论 |
|---|---|---|
| 1 | 模块书写语言 | 模块**只用 NS 写**; JS 能力走 `registerGlobal(name, obj)` 宿主注入, **不提供 JS 模块文件** (避免双加载管道/双错误边界/双类型系统) |
| 2 | JS 值互通 | NS 值底层即 JS 值 (number/string/array/bool 同源), 注入对象返回值限这四类, 其余视为非法值; 互通零转换成本 |
| 3 | 命名即对象名 | `use xxx` → 模块对象名 `xxx` (= 文件名); `use xxx as yyy` → 对象名 `yyy` |
| 4 | 免配置文件 | `use` 语句即激活声明, 不维护额外模块配置文件 |
| 5 | 符号归属 | 模块符号挂**模块命名空间对象**, 不进全局函数表, 与主程序全局零冲突 |
| 6 | 模块自包含 (黑盒) | 模块函数内查找链: **局部变量 → 模块私有全局 → 未声明报错**; 不访问主程序任何全局; `global.` 前缀在模块内指模块私有全局 |
| 7 | 模块与主程序交互 | 唯一通道: 调用 `xxx.函数(实参)` + 返回值; 模块函数不能读写主程序全局 (含 `global.` 前缀也不可及) |
| 8 | 调用形态 | **call 语句是函数专用入口**: 模块函数 `call xxx.func(a) -> r`, 与普通用户函数同一管道 → 函数体天然吃 NSVM 指令化; 表达式仅服务**词法内置对象** (Math.*/String.*/Bit.*/len 等, 与运算符同级) |
| 9 | 加载器可注入 | `setModuleLoader(name => 源码字符串)`; Node 默认 `fs` 读 `modules/`, 浏览器由宿主注入 (嵌入式刚需) |
| 10 | 模块内顶层动作 (已修订, 见 #25) | 模块顶层可执行语句**在被 use 时不执行** (加载时只执行 autoinit 块); 输出/错误来源标识 `[模块 xxx]` 仍强制适用; 顶层语句只在文件作为**程序入口**直接执行时才运行 (主逻辑) |
| 11 | 嵌套 `use` | 正式设计: 模块文件头部可有模块块 (依赖), 递归加载 + 跨文件幂等 + 循环检测 + 依赖封装 (见 §3.1) |
| 12 | 首版范围 | 无动态化限制, 栈/队列等动态结构均可写 (动态数组已定论不实施, 见 §8; 原"数组动态化设计成熟后再定"的解封条件已满足) |
| 13 | `use` 位置 (已修订, 见 #14) | **文件头部连续块**: 文件以 `debug N` 开头时紧跟其后, 否则从第一行起; 主内容区出现 `use` 报错; 头部区在加载期一次性处理, 先于 NSVM 编译 |
| 14 | 显式界定 | 用 `modules ... endmodules` 块显式划分头部区 (替代隐式扫描"实质性行"); 块内只允许 `use` + 空行 + 注释; 全文件至多一个且必须在头部; 无模块需求时可整体省略 (见 §2.3) |
| 15 | 同文件唯一命名与 `as` 用途 | 同一文件内一个模块只能 `use` 一次 (含别名), 重复报语法错误; `as` 用途 = 短名别名 + 避让与主程序命名冲突 + 未来多来源消歧 (单一 modules/ 目录下不存在"两文件撞同名"; 三分类目录后跨来源同名可共存, 多来源消歧改由 `from` 承担, 见 §2.2/确认记录 #24); 跨文件幂等: 模块实例全局唯一 (见 §2.2) |
| 16 | 动态结构约定 (元数据槽) | **确认**: 不实施语言级动态数组; 动态长度结构由"定长数组 + 元数据槽"承载 (栈/队列/集合等), 栈模块示例已验证可运行; 元数据槽是模块/主程序共用的书写规范 (见 §8) |
| 17 | 调用形态收敛 (词法 vs 过程) | **确认**: 函数 (用户/模块) 统一只走 `call` 语句, 表达式不调用函数; Math.*/String.*/Bit.*/len 等是**词法内置对象**, 与运算符同级, 定位为"内置函数跟运算符统一级别"; 无"表达式/语句"双写法, 无函数调用路径冗余 (见 §5.1) |
| 18 | 内置函数分类定稿 (2.7.2) | 内置函数分两类: **计算型** (`Math.*`/`String.*`/`Bit.*`/`len`/`str`/`int`/`float`/`copy`, "函数模样的运算符"——与运算符同级、无副作用, 可自由出现在表达式任何位置含 `&&`/`\|\|` 短路右侧) 与 **I/O 型** (`input()`, 与 `print` 关键字同属语言 I/O 通道——与外界交互是它的目的、有副作用, 不是"函数模样的运算符", 禁入短路右侧); §5.1 词法能力表同步此分类 |
| 19 | 模块边界语义 (定稿) | ① **mut 写穿与黑盒不冲突**: 调用方显式写 `mut` 且模块声明一致才允许 (不一致报错), 黑盒约束的是"不能隐式碰主程序变量", 显式 mut 传参是语言机制与普通函数一致 ② **边界严格性**: 数组形参/返回值在模块边界与主程序完全一致 (三档语义等), 不设第二套规则, 除不可避免的豁免外一律严格 ③ **错误冒泡**: 模块函数内错误与普通函数一致, 主程序 try-catch 可捕获; 无 catch 时错误消息与模块内行为语句 (print 等) 一样强制在开头显示 `[模块 xxx]` 来源标识, 被 catch 处理则不需要 ④ **加载期错误不可 try-catch**: use 失败/模块语法错误/依赖循环由模块管理器与加载器负责, 脚本作者无需操心 |

## 2. 语法

### 2.1 `use` 语句

```
use xxx               # 加载 modules/main/xxx/xxx/xxx.ns (来源缺省 = main), 模块对象名 = xxx
use xxx from yyy      # 加载 modules/yyy/xxx/xxx/xxx.ns (yyy ∈ main/extra/custom), 模块对象名 = xxx
use xxx as z          # 同 use xxx, 对象名改为 z
use xxx from yyy as z # 同 use xxx from yyy, 对象名改为 z
use inner xxx [as z]  # 加载当前包根下的模块 xxx (无 from, 写了 from 报错), 见 §3.4
```

- `use` 仅允许出现在头部 `modules ... endmodules` 块内 (见 §2.3), 主内容区 `use` 报错
- 模块对象名 = 模块名 (不带 `.ns` 后缀; 定位规则 `modules/{来源}/{包}/{模块}/{模块}.ns`, 见 §7.3)
- `from` 指定来源分类 (main/extra/custom), 缺省为 main (官方模块最常用, 少写来源)
- `as` 用于重命名 (短名别名 / 避让命名冲突, 见 §2.2)
- `use inner` 用于引用**当前包内**的模块 (模块拆分机制, 见 §3.4): 定位由当前文件所在包决定 (包根判定见 §3.4), 不需要 from

### 2.3 文件头部区结构 (显式模块块)

```
debug N              # 可选: 物理首行, 命令行 --debug 显式指定时忽略 (沿用现有优先级)
modules              # 模块块开始 (可选, 无模块需求时整个块省略)
use xxx
use yyy as z
endmodules           # 模块块结束
cmdargs ... endcmdargs  # 可选: 运行前参数 (入口文件, 见 §5.2)
autoinit             # 可选: 集中书写初始化代码的地方 (见 §3.3)
...
endautoinit
<主内容...>
```

规则:

- **头部区四级结构**: `debug` / `modules` 块 / `cmdargs` 块 / `autoinit` 块 **同级、互不嵌套** (块内不能再出现这四个块关键字), 各自**全文件至多一次**; `debug` 必须**物理首行**; 其余三块的先后为**建议顺序** (惯例 `debug → modules → cmdargs → autoinit`), **非强制** (cmdargs 放 modules 前、autoinit 放 cmdargs 前等均可)
- **`use` 只能出现在 `modules ... endmodules` 块内**: 主内容区与 autoinit 块内出现 `use` → 报错 (use 只能在模块块内)
- 全文件**至多一个** `modules` 块, 必须位于头部 (debug 之后或文件开头); `endmodules` 之后再用 `modules` 报错 (保持 "use 必须开头" 的意图)
- 块内**只允许** `use` 语句 + 空行 + 注释; 其他语句报 "模块块内只允许 use 语句"
- 未闭合检测: 有 `modules` 无 `endmodules`、或裸 `endmodules` → 语法错误 (复用现有块配对机制)
- `modules` / `endmodules` 为保留字 (NS 保留字本就禁止作变量名, 代价小)
- 无模块需求时整个块可省略, 文件与现有版本完全兼容
- 模块文件头部同样适用 (模块文件可含 `debug` + 模块块; 嵌套 `use` 见 §3.1)

### 2.2 幂等与冲突

- **同一文件内**同一模块只能 `use` 一次 ("同一模块" = **来源 + 模块名**组合: `use stack` 与 `use stack from main` 视为同一模块, `use stack from main` 与 `use stack from custom` 是不同模块), 重复 → 语法错误 "重复 use 模块 xxx"; 一个模块在同一文件内只有一个名字, 杜绝别名多命名
- **跨文件幂等**: 模块实例全局唯一, 全项目依赖图中每个模块只加载一次 (主程序与多个模块引用同一模块时共享实例)
- `as` 的真实用途 (来源已在 use 中由 `from` 显式区分, 不存在"来源歧义"):
  1. **短名别名** (便利性)
  2. **避让与主程序命名冲突**: 模块对象名可能与主程序全局变量/函数同名 (`global stack` 与 `use stack`), 用 `use stack as stk` 改名避让
- **跨来源同名可共存**: `use stack from main` 与 `use stack from custom` 是不同模块, 可同时 use; 两者对象名都叫 stack 会撞 → 编译期报错, 须给其一用 `as` (`use stack from custom as stk`)
- **inner 与平铺是不同模块**: `use inner tools` (当前包内) 与 `use tools from custom` (平铺独立包) 位置不同 → 是不同模块, 可同时 use; 对象名撞车同样用 `as` 避让
- 同一文件内 `use inner x` 重复两次 → 语法错误 "重复 use 模块 xxx" (与普通 use 同一规则)
- 不同模块被 `use` 成同一对象名 (`use a as x` + `use b as x`) → 编译期报错 (命名冲突)

## 3. 模块文件

位置: `modules/{来源}/{包}/{模块}/{模块}.ns`, 与解释器同目录 (见 §7.3)。模块文件是普通 NS 文件, 顶层内容:

| 顶层内容 | 语义 |
|---|---|
| `global` 声明 | 模块私有变量 (仅模块内可访问) |
| `:func ... :end` 定义 | 模块导出成员, 挂到模块命名空间对象 |
| `modules ... endmodules` 块 (可选) | 嵌套 `use`: 声明本模块的依赖 (见 §3.1) |
| `cmdargs ... endcmdargs` 块 (可选) | **运行前参数声明, 仅入口文件生效**; 非入口 (被 use) 写了**不报错不生效**, 参数保持默认值 (见 §5.2.2) |
| `autoinit ... endautoinit` 块 (可选) | **加载时执行的初始化代码** (两种加载路径都执行: 程序入口与被 use, 见 §3.3) |
| 可执行语句 | **主逻辑**: 仅文件作为**程序入口**直接执行时运行; **被 use 时不执行** (见确认记录 #25) |

- **输出/错误来源标识**: 模块内**所有**输出 (autoinit 动作与模块函数体内的 `print` 等行为语句) 强制在开头显示 `[模块 {来源}/{包}/{模块}]` 来源标识 (如平铺模块 `[模块 main/stack/stack]`、inner 子模块 `[模块 custom/mylib/helpers]`; 带来源与包名 → 跨来源同名/跨包同名模块标识不混淆); 模块内未捕获的错误同样带来源标识, 被主程序 catch 处理则不需要 (见确认记录 #19); 实现方式 = **解释器侧强制前缀** (i18n 模板只负责措辞, 前缀机制是解释器强制的, 见确认记录 #22)

### 3.1 嵌套 use (模块依赖)

- 模块文件头部语法与主程序完全一致: 可选 `debug` + `modules ... endmodules` 块
- **递归加载**: 主程序 `use A` → A 头部 `use B` → 先加载 B 再加载 A
- **跨文件幂等**: 全项目依赖图中每个模块只加载一次 (见 §2.2)
- **循环检测**: A → B → A 报语法错误 "模块依赖循环"
- **封装**: A use 的 B 只在 A 的文件作用域内可见 (A 的函数体内可调 `B.func`), **对主程序/其他模块不可见** —— 依赖不泄漏; A 的命名空间对象只含 A 自身导出的成员

- 模块函数体: 与普通函数体一致 (局部变量/数组/错误处理/try-catch 全部照常), 且走 NSVM 函数调用管道

### 3.2 include 文件合并 (已关闭, 确认记录 #25)

**include 机制不引入。** 模块拆分由 **平等模块 + `use inner`** 解决 (见 §3.4), 不提供文件合并/拼代码机制:

- 当初设想的 include (通用文件合并: 主程序/模块共用, 成员自动提升) 因头部指令冲突 (debug/modules/cmdargs) 与"写法统一"原则的矛盾而作废
- 拆分需求由包内多模块承载: 包内模块都是**完整 NS 模块** (写法与普通模块完全一致), 通过 `use inner` 引用, 无需特殊片段语法

### 3.3 autoinit 块 (自动初始化)

```
autoinit
# 初始化代码: 集中书写
endautoinit
```

- 定位: **集中书写初始化代码的地方** —— 模块被 use 时, 解释器只执行 autoinit 块内的内容作为**自动初始化**, 顶层语句不执行; 不规定块内能写什么 (autoinit 本身就是"初始化代码区")
- **与正文同级别、共享同一空间**: autoinit 不是独立作用域 —— global 声明与函数定义加载期**全文件统一建立** (与书写位置无关), autoinit 内可自由引用正文声明的 global、调用正文定义的函数; 与正文的差别只在**执行**: 被 use 只执行 autoinit, 入口脚本 autoinit 与正文都执行
- 位置: 头部区, 与 modules/cmdargs 同级 (见 §2.3); 全文件**至多一个**
- **两种加载路径** (确认记录 #25):

| 路径 | autoinit 块 | 顶层语句 (主逻辑) |
|---|---|---|
| 程序入口 (解释器直接执行) | 执行 | 执行 |
| 模块加载 (被 use) | 执行 | **不执行** |

- **跨身份通用**: autoinit 是两种加载路径**都执行**的初始化入口 —— 文件无论作程序入口还是模块, autoinit 都执行 (每次加载只执行一次), **初始化逻辑不因身份丢失**; 与正文的差别只在入口场景正文 (主逻辑) 额外执行
- 意义: 需要**动态初始化**的模块 (NS 声明初始化只允许字面量, 动态值需赋值语句) 把初始化代码集中写进 autoinit; 纯静态模块 (字面量 global + 函数) 不需要
- **项目 → 模块迁移**: 主逻辑组织成函数, 顶层只留一句 `call 主逻辑()`; 作程序时顶层跑 (启动), 作模块时顶层不跑, 调用方 `call 模块.主逻辑()` 手动启动; **边界**: 若把主逻辑调用写进 autoinit (如 autoinit 内 `call 主逻辑()`), 模块被 use 时主逻辑也会自动执行 (加载即启动) —— 作者自由选择, 与"autoinit 只放初始化"的惯用法不同

### 3.4 模块拆分: use inner 与包

**拆分 = 把大模块拆成同包内的多个模块**, 用 `use inner` 互相引用 (包内模块关系: 与包名同名的模块是**主模块 (入口模块)** —— 包被 use 时加载的即它; 其余是**子模块**; 结构上所有模块都是完整 NS 模块, 主模块只是名义上的入口):

```
modules/custom/mylib/            # 包根 (包名 = mylib) —— 包根下是模块的集合
├── mylib/
│   └── mylib.ns                 # 模块: 主模块 (入口模块, 目录与包名同名)
└── helpers/
    └── helpers.ns               # 模块: 子模块
```

结构说辞恒为 **`包/模块/模块.ns`**: 包根下是**模块的集合** (无"包里的包", 主模块只是与包名同名的模块, 不是"包里的包"); 包内模块**关系**: 与包名同名的模块是**主模块 (入口模块)**, 其余是**子模块** (子模块用 `use inner` 引用主模块/其他子模块)。

```
// mylib/mylib.ns
modules
use inner helpers       # 无 from; 写了 from 报错
endmodules
```

- `use inner x` → **当前包根**`/x/x.ns`; **定位**: 包内文件路径恒为 `包根/{模块}/{模块}.ns` → **当前包根 = 当前文件路径上两级目录** (无需查找); **校验包根**: 包根目录须含 `manifest` 且 `manifest.package == 包名`, 否则 = 无包 → `use inner` 报错; **校验模块**: x 须在 `manifest.modules` (包根下模块目录名集合) 中, 不在 → 报错 "包内无此模块 x"; 最后定位 `包根/x/x.ns` (manifest 字段见 §9.1)
- 仅**包内文件**可用 (单文件脚本无包, 写 inner 报错)
- 包内模块都是完整 NS 模块 (独立命名空间、封装、依赖全部照常); **对包外不可见** (`use x from S` 定位不到包内的 x) —— 半私有: 想公开就平铺成独立包
- 程序形态的包 (包根在项目根) 的主模块的脚本同样可用 inner 引用其包内模块

## 4. 命名空间与作用域

- 模块符号挂**模块命名空间对象**, **不进全局函数表** → 与主程序全局/函数零冲突, 无需改名
- 模块函数内变量查找链 (固定两跳):

```
局部变量 → 模块私有全局 → 未声明报错
```

- `global.` 前缀在模块内 = **强制访问模块私有全局** (块级作用域局部遮蔽时使用), 语义与主程序内 `global.` 强制访问全局对称
- 模块函数内不可声明全局 (与现有"函数内不可声明全局"规则一致)
- 模块是**黑盒**: 不读不写主程序任何变量, 与主程序交互只有"实参进 + 返回值出"; `mut` 显式写穿是调用方授权的语言机制 (调用方写 `mut`、模块声明一致才允许, 不一致报错), 与黑盒不冲突 (见确认记录 #19)

## 5. 调用形态 (单入口: call 是函数专用)

**函数 (用户/模块) 只有一条调用路径: `call` 语句。表达式不调用函数** —— 表达式里出现的 `Math.*`/`String.*`/`Bit.*`/`len` 等是**词法内置对象**, 与运算符 (`+` `-` 等) 同级, 不是"函数" (详见 §5.1)。

| 形态 | 示例 | 路径 |
|---|---|---|
| 语句 | `call tools.min(a, b) -> y` | `executeCall` 名字解析扩展模块前缀 → 同一调用管道 |

模块函数与普通函数共用同一调用管道 → 函数体编译为指令 (NSVM), 不牺牲性能。

> 语句入口前置 (2.7.2 起为纯占位): `executeCall` 名称解析**暂只支持单一标识符** (模块函数前缀 `xxx.func` 待模块系统实现时引入); NSVM 编译 CALL 正则不含点分 → 含点分名的 call 语句整体回退行解释器, 零 NSVM 改动。**模块系统实现时反转此策略**: 点分 call 必须编译进 NSVM (CALL 指令支持模块命名空间寻址), 见 §7.5 实现注意点 ①。

### 5.1 词法能力 vs 过程 (分层定位)

**语言能力分三层, 调用形态由层级决定, 不重叠 (2.7.2 分类定稿):**

| 层级 | 成员 | 调用形态 |
|---|---|---|
| 词法能力 (与运算符同级) | 计算型内置函数: Math.* / String.* / Bit.* / len / str / int / float / copy | 表达式 `y = Math.min(a, b)` (可嵌套运算, 无副作用) |
| I/O 通道 (与外界交互) | `print` 关键字 (输出) / `input()` 函数 (运行中输入) / `cmdargs` 块 (启动参数, 声明式接收) / `cast.类型` (两条输入通道共用的接收类型) | `print x` 语句 / `s = input()` 表达式 / `cmdargs ... endcmdargs` 声明式块 (见 §5.2); 不是"函数模样的运算符", `input()` 禁入 `&&`/`\|\|` 短路右侧 |
| 过程 (函数) | 普通用户函数 / 模块函数 | 只能 `call f(a) -> y` 语句 |

- **函数单入口 (定稿)**: 用户函数与模块函数统一走 `call`, 无"表达式/语句"双写法; `call` 的功能不被削弱 —— 动作、数组容器填充、`mut` 写穿、数组返回值、void 全部由 `call` 承载, 表达式本就不承担这些
- **定位依据**: Math 之类是**解释器内置能力**, 跟运算符一样是词法的 (作者原话: "math 之类的定位就是内置函数跟运算符统一级别"); 函数是程序的过程抽象, 与 `if`/`for` 同级, 用语句调用
- **同形不变**: §6 的"名字.函数()"在 call 语句下依然成立 (`call tools.min()` / `call injected.obj()`), JS 注入对象与 NS 模块写法无差别
- 代价 (已接受): `y = tools.min(a, b) + 1` 的嵌套写法不可用, 需先 `call` 到中间变量再运算 —— 符合"函数调用是语句"的语言风格
- 与历史一致: 语言自始不支持用户函数进表达式 (表达式里报"未知函数"), 本定稿只是把该现状确认为设计, 而非缺陷

### 5.2 运行前参数 (cmdargs) (设计定稿, 确认记录 #23)

**背景**: 语言无 argv; NS 脚本需要接收运行前参数 (命令行参数) 的能力 (而非只能靠 `input()` 互动式输入) —— 由运行前参数机制解决, 不把 argv 概念引入语言内部; **cmdargs 是语言级能力, 独立于模块系统** (模块管理器这类运行前工具只是使用者之一, 见 §5.2.8)。

#### 5.2.1 I/O 层全景

**外部世界进语言的只有字符串**; 四条 I/O 通道:

| 机制 | 方向 | 形态 |
|---|---|---|
| `print` | 语言内部值 → 外部 (输出) | 关键字 |
| `input()` | 外部 → 语言内部 (运行中输入) | 函数, 返回字符串 |
| `cmdargs` 块 | 外部 → 语言内部 (启动参数) | 声明式接收 |
| `cast.类型` | 外部字符串 → 类型化变量 | 类型 (input() 与 cmdargs 共用) |

cast 是两条输入通道 (input() / cmdargs) 共用的"字符串 → 类型化变量"接收类型 (详见 §5.2.5)。

#### 5.2.2 cmdargs 块

- **位置**: 脚本头部 (debug 指令之后、主内容之前), 与 modules 块同级 (§2.3)
- 全文件**至多一个**、只能出现一次
- **只对入口文件生效** (确认记录 #25): 参数只传给被解释器直接执行的文件; 非入口文件 (被 use 的模块) 写了 cmdargs **不报错、不生效**, 参数保持默认值
- 模块作者两手准备: 作入口时收命令行参数, 被 use 时靠 API 传参
- **绑定时机**: 入口文件的 cmdargs 参数在**执行前**完成解析与绑定, **先于 autoinit 与正文执行** —— autoinit 内可直接使用 param (已绑定为命令行值或默认值); autoinit 与正文**同级别、共享同一空间** (见 §3.3), 作模块被 use 时只执行 autoinit (cmdargs 不生效, 参数保持默认值)

#### 5.2.3 param 声明

两种写法:

```
param cmd:string = "help"          // 写法一: 无短名, 命令行用 --cmd
param verbose:bool = false as "v"  // 写法二: 带短名, 命令行额外可用 -v
```

- 语法: `param 名:类型 = 默认值`, 后面可再跟 `as "短名"` 提供短参数别名
- 类型: string / bool / cast.int / cast.float
- 命名规则与普通变量完全一致 (允许的字符集、禁止关键字等)
- 默认值必须有 (与普通变量声明一致, 只能是字面量, 不豁免)
- 短名写法: as 后写不带横杠的名字, 命令行里用 `-短名 值`, 与 `--全名 值` 并存
- param 变量只读, 程序内修改报错 (与 const 一致); 需改写就先读出赋给普通变量

#### 5.2.4 命令行匹配与填充

- **匿名**: 不带横杠开头的参数, 按声明顺序匹配
- **全名**: `--名字 值`; **短名**: `-短名 值`
- **混合顺序**: 先处理所有带横杠开头的有名参数; 再从剩余未赋值的 param 中按原声明顺序重排; 最后把不带横杠的裸参数按重排顺序填充
- 匿名参数比声明少: 少的用默认值
- 匿名参数比声明多: 多的丢弃并给出警告
- 未知有名参数 (命令行写了但脚本没定义): 报错 (基本是拼写错误)
- bool 参数: 传入即翻转默认值, 不传保持默认值, 后面紧邻的东西不归它管
- string 和 cast 类型的参数: 必须消费后面紧邻的一个值, 后面没值就报错
- 脚本参数区内不允许孤立的 `--`: `--` 必须紧跟字母组成 `--名字`, 单独的 `--` 报错

#### 5.2.5 cast 类型

- **语法**: `cast.int`、`cast.float`
- **语义**: I/O 边界的接收类型 —— "这个变量接收外部来的字符串值, 按 int()/float() 的语义转换后再存"
- **应用**: cmdargs 的 param (`param age:cast.int = 0`); input() 赋值 (`ratio = input()`, ratio 声明为 cast.float)
- 转换失败 (int("abc") 得到 NaN) 报错, 错误消息标注变量名
- 转换后是纯粹的 int/float, 可正常运算比较
- **不提供 cast.number**: 提供也只是走 cast.float 的老路; 参数类型保持 int/float 二选一的明确
- 不影响语言内部类型系统: 普通变量声明没有 cast, int()/float() 仍是纯粹转换函数

#### 5.2.6 命令行两层结构

```
node dist/noethingScript-Interpreter.js --debug 1 script.ns -- arg1 arg2 ...
```

逐段含义:

1. `node dist/noethingScript-Interpreter.js`: 解释器编译产物, 启动解释器
2. `--debug 1`: 解释器自己的参数
3. `script.ns`: 脚本路径
4. `--`: 独立记号, 从这里开始后面都归脚本
5. `arg1 arg2 ...`: 脚本参数区 (arg 是占位名, 省略号表示后面还可以有更多参数), 按 cmdargs 规则解析

`--` 是一个完整的独立 token (前后空格隔开), 与 `--name` (横杠紧跟字母) 天然不冲突。

#### 5.2.7 按定义切分 (两步流程)

1. **命令行解析**: 挑走解释器参数、确定脚本路径、确定 `--` 后的脚本参数串 (先不切分)
2. **按 cmdargs 定义切分**: 解析脚本头部 cmdargs 定义, 照定义切分——bool 是开关 (不吞后面的值), string 和 cast 吞后面紧邻的一个值, 不带横杠的是匿名参数

例: `param debug:bool = false` 时传 `--debug 1` → debug 变 true、1 是独立匿名参数 (两个); `param debug:cast.int = 0` 时同样传 `--debug 1` → debug 就是 1 (一个)。

#### 5.2.8 与模块管理器的关系

cmdargs 是**语言级能力** (脚本接收运行前参数), 独立于模块系统存在; 模块管理器这类"运行前工具"只是使用者之一。管理器模块本身的设计见 §9 (模块管理器, 已定稿, 确认记录 #26)。

#### 5.2.9 显式性保证

- 不写 cmdargs 块就没有接收参数的能力, 不会凭空冒出可读的名字
- cast 字面写着"转换", 小白看到就知道参数本来是一串字符串
- 没有隐式对象、没有隐式转换、没有类型豁免

## 6. JS 能力分层 (与宿主桥接合流)

```
语法层 (模块书写语言)  →  只用 NS, 统一
能力层 (谁能提供函数)  →  NS 模块 + registerGlobal 注入的 JS 对象, 都行
```

- JS 注入对象与 NS 模块在 NS 代码中**同形**: 都是 `名字.函数()`, 脚本作者无感知
- 值互通 (NS 值底层即 JS 值):

| NS 类型 | 底层真身 | JS 侧 |
|---|---|---|
| int / float / number | `number` | 数字 |
| string | `string` | 字符串 |
| array | `Array` | 数组 |
| bool | `boolean` | 布尔 |

- 约束: 注入对象返回值限于上述四类; 返回对象/函数等视为非法值并报错

## 7. 加载机制 (框架已定稿, 细节见各小节)

### 7.1 loader 同步原语

- 加载器可注入: `NSI.setModuleLoader(name => 源码字符串)`, **同步返回**源码字符串 (不返回 Promise)
- 核心只调用 loader 拿字符串, 不做 I/O; 阻塞与否取决于 loader 实现
- Node/CLI 默认: `fs` 按定位规则读文件 (模块文件 KB 级, 一次性启动成本, 可忽略)
- 浏览器: 宿主预取 (运行前 `await Promise.all(fetch...)` 存 map), loader 同步查 map —— **不引入 async 加载链**, 加载→编译→执行保持同步; 异步能力归模块管理器 (§9.1), 不压核心

### 7.2 两阶段加载

- **阶段 1 依赖图构建与检查**: 扫描主程序头部 `use` → 递归读模块源码头部 (解析内部 `use`) → 构建全项目依赖图; 检查: 模块存在 (loader 可取得)、无循环依赖、无命名冲突; 有问题在此阶段报错, 不进入加载
- **阶段 2 批量加载**: 检查全部通过后, 按依赖顺序 (先依赖后自身) 批量加载模块——编译模块源码、创建命名空间对象、挂载导出成员
- **源码缓存**: 阶段 1 读过的模块源码存内存, 阶段 2 直接复用 (每模块只读一次; 模块文件全量读入, 头部解析与加载共用)

### 7.3 模块目录与命名 (三层结构, 确认记录 #25)

- 默认 `modules/` (解释器同目录); 命令行与浏览器均可配置**唯一**模块目录 (不支持多个模块目录)
- 目录 = 三层: **来源分类 → 包 → 模块** (模块文件夹 + 同名脚本):

```
modules/
├── main/                    # 官方模块 (目前即作者本人)
│   └── stack/               # 包 (包名 = 主模块名)
│       ├── manifest         # 包元数据 (JSON, 见 §9.1/确认记录 #28/#29)
│       └── stack/
│           └── stack.ns     # 模块: 主模块 (入口模块, 与包名同名)
├── extra/                   # 收录的第三方模块 (设想)
│   └── queue/
│       ├── manifest
│       └── queue/
│           └── queue.ns
└── custom/                  # 自制或松散渠道获得的模块
    └── mylib/               # 包: 模块的集合 (主模块 + 子模块)
        ├── manifest
        ├── mylib/
        │   └── mylib.ns
        └── helpers/
            └── helpers.ns
```

- **符合规范的包根含 `manifest`** (JSON, 记录 package/version/ns/source/command/description/modules, 见 §9.1/确认记录 #28/#29): 管理器安装/建索引据此读版本与适配, `use inner` 据此定位与校验 (见 §3.4); **无 manifest 的包 → 标记不合规范** (提示补 manifest, 版本/适配留空)

- 定位规则: `use xxx from yyy` → `{模块目录}/yyy/xxx/xxx/xxx.ns` (yyy ∈ main/extra/custom, **包名 = 模块名 = 模块脚本名**); `use xxx` (无 from) → `{模块目录}/main/xxx/xxx/xxx.ns` (默认官方)
- `use inner x` → `{当前包根}/x/x.ns` (包内模块, 见 §3.4)
- 模块对象名 = 模块名 (见 §2.1); 跨来源同名模块可共存 (`main/stack` 与 `custom/stack`)
- **包内子模块对包外不可见**: `use x from S` 定位不到包内的 x (见 §3.4); 想公开就平铺成独立包
- **不设"大类"目录层, 不引入类型元数据**: 大类靠模块名语义 (stack/queue/set 即数据结构); 包 = 项目/模块集合 (程序 = 包 = 模块统一, 见确认记录 #25)

> **备忘录 (新手提示)**: 三层中"包名 = 模块名 = 模块脚本名"同名 (如 `main/stack/stack/stack.ns` 三层都叫 stack) 看起来重复, 这是"程序 = 包 = 模块"统一形态的代价——包根搬位置即变身 (项目根 = 程序 / modules/ = 模块), 换来零代码迁移。不必深究, 按模板建目录即可; 详细组织方式与示例留给 doc 的模块手册 (后议)。

### 7.4 加载期错误 (标注模块名)

- 找不到模块: `[ERROR] 模块 'tools' 不存在 (modules/main/tools/tools/tools.ns)`
- 模块语法错误: `[ERROR] 模块 'tools' 语法错误: ...`
- 循环依赖: `[ERROR] 模块依赖循环: tools -> utils -> tools`
- 加载期错误 (use 失败/模块语法错误/依赖循环) **不可 try-catch**: 由模块管理器与加载器负责, 脚本作者无需操心 (见确认记录 #19)
- 模块内动作输出强制带模块名标识 (见 §3)

### 7.5 性能模型 (确认记录 #30)

**目标**: 模块系统不牺牲性能 —— 模块函数调用与普通函数同价, 加载成本与模块数量线性, 无隐藏的逐调用开销。

**运行期 (热点路径, 零额外开销)**:

- 模块函数与普通函数**共用同一调用管道** (见 §5), 函数体编译为 NSVM 指令 → 模块函数调用与普通函数性能完全相同, 无解释器双管道
- `call xxx.func(a)` **编译期**把 `xxx.func` 绑定到模块命名空间成员, 运行期直接指令执行, 无字符串查找
- 模块内查找链两跳: 局部 → 模块私有全局 → 报错 (见 §4), 与主程序 (局部 → 全局) 同构, 无第三跳
- 值互通**零转换**: NS 值底层即 JS 值 (确认记录 #2), 模块边界传参/返回无转换成本
- 来源标识 `[模块 xxx]` 只走输出/错误路径, 不进计算路径

**加载期 (一次性, 与模块数量线性)**:

- 两阶段 + 源码缓存 (见 §7.2): 阶段 1 只读模块头部扫 use, 阶段 2 编译一次; 每模块源码只读一次
- 跨文件幂等 (见 §2.2): 全依赖图每模块只加载一次, 总成本 = 各模块编译一次之和, 无重复加载
- 相对普通脚本的额外成本: 文件读取 + 头部 use 扫描 + 命名空间建立 + 模块函数编译 —— 一次性; 模块文件 KB 级 (见 §7.1), 可忽略

**内存**: 每模块 = 命名空间对象 + 编译产物 (指令数组); 模块实例全局唯一, 无重复加载占用

**实现注意点 (兑现"不牺牲性能"承诺的关键)**:

1. **点分 call 必须 NSVM 编译**: §5 语句入口注记中"含点分名的 call 整体回退行解释器"是 **2.7.2 占位期策略** (模块系统未实现时); 模块系统实现时**反转此策略** —— CALL 指令支持模块命名空间寻址, `call xxx.func` 编译进 NSVM, 否则点分调用全部掉进行解释器, 性能反而不如普通函数
2. **源码释放**: 加载完成后释放模块源码字符串, 只保留编译产物与命名空间 (源码缓存只服务加载期, 见 §7.2)

**结论**: 运行期与普通函数同价, 加载期一次性成本与模块数量线性。守住上述两条注意点, 模块系统性能等价于同量代码写在单个文件里。

## 8. 动态结构约定 (元数据槽模式)

> 状态: **已确认** (确认记录 #16)。原"数组动态化"待定项结论定论: **不实施语言级动态数组**。

- 结论依据: 动态长度结构 (栈/队列/集合等) 可由**定长数组 + 显式状态**完全承载, 无需语言级"有界动态"机制; 语言保持"静态/显式/可预测"初衷, 核心零改动, 保住 24/24 逐字节回归红线
- 模式: **元数据槽** —— 数组 `st[0]` 存逻辑状态 (如栈顶下标, 空栈=0), 数据从 `st[1]` 起, 数据容量 = `len(st) - 1` (容量由声明方决定, 使用者用 `len(st)` 动态读取, 不写死); 越界 (空栈 pop / 满栈 push) 用 `assert` 显式报错不静默
- 栈顶为何不能用显式 int 引用: `mut` 关键字仅对数组参数有效, int 无引用传递 → 元数据槽是唯一正解
- 覆盖边界: 元数据槽覆盖**单层动态结构** (栈/队列/集合/池); 嵌套引用结构 (树/图/链表) 需元素存引用, 而数组元素为标量值存不了数组引用 —— 这属"引用类型"问题, 与动态数组无关 (动态数组元素同样存不了引用), 故动态数组两头都不占, 确认关闭
- 栈模块示例 (按 2.7.0 数组形参元素类型语法验证可运行, 含 `st[st[0]]` 嵌套下标 / assert 块 / mut 匹配规则):

```ns

:end

:push (mut st[]:int, v:int) -> :void

"栈已满: 容量 " + (len(st) - 1)
endasrt
st[0] = st[0] + 1
st[st[0]] = v
:end

"栈为空"

:end

:peek (st[]:int) -> v:int

"栈为空"
endasrt
v = st[st[0]]
return v
:end
```

### 8.1 嵌套引用结构 (对象池 / 平行数组句柄)

- 链表/树/图等嵌套引用结构: 数组元素为标量值, 无引用类型, 亦不允许"数组的数组"; 用**平行数组 + 整数索引句柄**承载 (对象池模式), 与 C 语言"数组模拟指针"同构
- 模式: 节点池由 N 个平行定长数组表示 (值 / 左子 / 右子 / 空闲链各一数组), 节点身份 = 数组下标 (句柄), `-1` = 空引用; 空闲节点用空闲链维护 (alloc/free)
- 已验证: 单链表 push-front / 遍历 / 空闲池分配实际运行通过 (含 `node_next[free_head]` 句柄链)
- 多维数组: 一维数组 + 下标计算 (`matrix[1 * COLS + 2]`), 见 doc.md "多维数组实现"
- 键值映射: 平行 key/value 数组 + 线性查找 (O(n)); 哈希表需 `registerGlobal` 桥接

### 8.2 能力边界 (无论如何实现不了)

| 能力 | 状态 | 说明 |
|---|---|---|
| 函数作为值 (回调/高阶/函数指针) | **实现不了** | 函数不能赋值给变量、不能作实参传递; 排序比较器/事件回调等无表达路径 |

## 9. 模块管理器 (确认记录 #26, 原"待定事项"章节转正为正式章节)

### 9.1 总览 (定位/形态/职责/环境/参数/安装目标)

- **定位: 运行前工具 (init 地位)**: 类比 Linux init——系统启动的第一个程序, 自举 (能管理自己的版本/自更新); 管理器**不依赖任何模块** (自包含), 需要解释器运行
- **形态: 独立 NS 程序, 单入口 + 子命令**: 管理器自己是主程序 (无 `call mgr.xxx` 超长前缀问题), cmdargs 接收子命令参数; **管理器本身作为模块发布到模块仓库** (如 `main/nsm`), `update nsm` 即可更新自己 —— **无 self-update 命令**
- **职责: 获取与组织模块文件 + 递归获取依赖**: 安装时解析模块头部 `use` 递归获取依赖 (避免运行时才发现缺模块); 核心加载器运行时仍做依赖图检查 (防御性, §7.2, 正常已装全不会缺)
- **运行环境: Node/CLI 专用**: 依赖 `registerGlobal` 注入的 fs/http 能力; **浏览器下不存在管理器形态** —— 网页的模块文件在本地网页开发时确定好、随网页一起提供 (把管理器上传到网页也不会发挥作用); 本地网页开发时用的仍是命令行管理器
- **入口参数已定稿**: 管理器程序接收命令参数 (install/update/list) 由**运行前参数 (cmdargs)** 机制解决 —— 语言无 argv, cmdargs 块在脚本头部声明 `param` 接收启动参数 (见 §5.2, 确认记录 #23)
- **运行方式**: 管理器在 manifest 声明命令 `nsm` (命令 = 主模块的脚本路径的别名, 确认记录 #27) —— 运行 `node <解释器路径> nsm -- <子命令> [参数]` (解释器把 nsm 解析为主模块的脚本路径, 等价于 `node <解释器路径> modules/main/nsm/nsm/nsm.ns -- install stack`); 日常少打 `--` 可用 shell alias
- **安装目标已定稿**: 管理器把模块文件放到 `modules/{来源}/{包}/{模块}/{模块}.ns` (来源缺省 main, 见 §7.3)

**模块来源 (独立模块仓库)**
- **仓库与解释器仓库分离** (解释器包不背模块体积), **GitHub 主 / Gitee 镜像**: 基址可配置 (网络失败可切换), 两镜像 URL 结构相同 (`{基址}/{来源}/...`)
- 一个仓库, **顶层目录 = 来源分类** (`main/` / `extra/`)
- **打包粒度 = 包**: 一个包一个压缩包 (含主模块 + 全部子模块), 解压即 `modules/{来源}/{包}/`; 命名 `包名@模块版本-v适配解释器版本.zip`
- **拉取协议 = http 按路径下载压缩包** (不用 git clone, 按单包拉取)
- **索引清单 (manifest)**: 每来源一个, 条目 = 来源 / 包名 / 模块版本 / 适配解释器版本 / 压缩包文件名; 清单加字段向后兼容 (老管理器忽略新字段 = 能力变强非破坏)
- **依赖不由清单标注**: 安装后扫描包内文件头部 `use` 自动发现依赖再递归拉取 (管理器是 NS 程序, 解析自家语法, 符合自举哲学)
- 安装流程: 拉 manifest (缓存) → 查包 → 下载压缩包 → 解压安装 → 扫描依赖递归
- **custom 纯本地, 不联网** (仓库只有 main/extra): ① `install <本地压缩包路径>` 安装 (不带 from, 由包内 manifest.source 决定; 包名须符合规范, 解压到 `modules/custom/{包}/` 并重建 custom 索引, 体验同 dnf 本地包安装); ② 手动把**符合规范的包文件夹**直接放进 `modules/custom/` 后, 执行 `refresh custom` 重建 custom 本地索引 (list/search 才能看到)
- **custom 本地索引**: 扫描 `modules/custom/` 下包文件夹生成, 记录包名与版本/适配 (有 manifest 读 manifest; 无 manifest → **标记不合规范**, 提示补 manifest, 版本/适配留空)

**版本适配 (防破坏性更新)**
- **NS 版本语义 (项目自有约定, 非 semver)**: **中间位 (minor) 变化才可能引入破坏性变更** (2.7.x 集中破坏性更新, 2.8.0 引入模块系统), patch 变化不破坏 (§10.1)
- **适配版本 = 前两段** (如 `v2.8`); 匹配规则: 当前解释器**前两段** == 适配版本 → 匹配; 不等 → 警告 "模块适配 v2.8, 当前 v2.9, 可能不兼容", `--force` 可强制安装
- 压缩包命名含适配版本: `stack@1.2.0-v2.8.zip`

**版本覆盖规则 (防误操作)**
- **升级** (高版本覆盖低版本): 正常路径, update/upgrade 专用
- **降级** (install 显式 `@` 低版本覆盖已装高版本): **警告 + 需确认, `--force` 跳过**
- **换源** (同名不同来源覆盖, 如 main/stack 已装再装 custom/stack): **确认, `--force` 跳过**
- `update` / `upgrade` **只升不降** (永远不主动降级)

**命令集 (单入口 + 子命令)**

| 命令 | 语义 |
|---|---|
| `install <包名 [from <来源>] \| 本地压缩包路径> [@<版本>]` | 包名 + from main/extra (**from 缺省 main**): 拉清单 → 下载压缩包 → 解压安装 → 扫描 use 递归依赖; 本地压缩包路径: **不带 from (写了 from 报错)**, 装到哪由包内 manifest.source 决定 (同名已有一律确认 + `--force`), 适配检查 (zip 文件名/manifest 适配版本, 不等警告 + `--force`), 解压到 `modules/{来源}/{包}/` 并重建索引; 覆盖规则见上 (降级/换源需确认 + `--force`) |
| `update [<包>]` | 模块更新到**适配当前解释器**的最新版 (安全更新, 解释器不变; 无参 = 全部模块) |
| `upgrade [<包>]` | 模块**跨适配段**大升级 (含确认, `--force` 跳过; 无参 = 全部模块) |
| `check-update [<包>]` / `check-upgrade [<包>]` | 只查不装 (无参 = 全部, 报告有无新版本/适配变化, 默认强制刷新清单) |
| `refresh <main\|extra\|custom> \| all` | 重建指定仓库的本地索引/清单缓存: custom 重扫 `modules/custom/` (手动丢包文件夹后执行), main/extra 强制重拉远程清单, all 刷新全部 |
| `list` | 已安装模块 + 孤立标记 |
| `search <关键词>` | 本地索引包名子串 (main/extra 清单缓存 + custom 本地索引, 不联网; 缓存过期即自动重拉, 手动最新走 refresh) |
| `remove <包> [from <来源>]` | 只删指定包 (**from 缺省 main**), **不动依赖** (孤立包由 list 标记——管理器看不到主程序 use, 自动清理有误删风险) |

> **本地压缩包安装 (定稿, 确认记录 #28/#29)**: `install <本地压缩包路径>` **不带 from (写了 from 报错)** (远程 from 是"来源", 本地装到哪由**包内 manifest** 决定 —— 来源身份包自携带, 两语义干净分离); **来源安全**: 远程安装来源由拉取路径强决定 (main/ 拉的装 main), 且 **manifest.source 与拉取来源不一致 → 警告并阻止安装**, 需用户手动 `--force` 强制安装 (规避篡改风险); 本地安装按 manifest 来源装, **目标已有同名包一律确认、`--force` 才覆盖** (伪造来源的兜底); 流程 = 管理器读 zip 内 manifest → 适配检查 (zip 文件名/manifest 适配版本, 不等警告 + `--force`) → 解压到 `modules/{来源}/{包}/` → 重建索引; **manifest**: 包根 `modules/{来源}/{包}/manifest`, JSON (node 原生), 字段 package/version(x.y.z)/ns/source/command(数组)/description/**modules**(包根下模块目录名集合, use inner 校验, 见 §3.4), 必选 package/version/ns/source (缺一或解析失败 → 不合规范), 且 **`manifest.package == 包目录名`** (不一致 → 不合规范/安装报错; 打包工具 nsmp 生成时保证, 手写/丢包需校验), 未知字段忽略; **打包工具 = 独立包 `nsmp`**: 扫描包目录自动生成 manifest (包名=目录名、依赖=扫 use、**modules=扫模块目录集合**, version/source/command 参数提供, ns 默认打包时解释器版本), 作者零手写, 手写仍合法; 打包只管产物 (zip 上传/清单更新作者 git 手动); **无 manifest 丢包 → 标记不合规范** (版本/适配留空); **依赖获取**: 扫描包内 use (性能差距可忽略——安装主导开销是下载/解压; use 权威不失真, manifest 标注副本会漂移; 加载器运行时本就扫 use 建依赖图), manifest 不标依赖; **search**: 默认本地索引, 缓存过期自动重拉, 不加 `--refresh`。

**解释器更新分工**
- **解释器本体自己负责更新**: Node 原生网络能力, 接受参数自查自更 (如 `ns --check-upgrade` / `--upgrade`); 管理器不管解释器, upgrade 只管模块
- 将来用 NS 重写解释器后, 是否进模块仓库统一管理为**可选** (解释器有网络注入则继续自更也行)

**清单缓存 (依赖缓存/索引)**
- **DNF (Fedora) 模型**: 清单本地缓存 + **TTL 写死 7 天** (未过期直接复用, 过期自动重拉; 个人项目更新低频) + `check-update`/`check-upgrade` 默认强制刷新
- TTL 先写死 (省掉配置文件机制, 减负担); 以后有需求再缩短或开放配置 (向后兼容)
